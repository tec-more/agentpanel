## 0. 复审说明

### 0.1 为什么必须复审

首轮评审（本报告同目录首份报告）在评审当天上午完成，其全部判断建立在 PRD v1.0 §1.1 的产品定位之上：「把开源 AI Agent 客户端改造成可商业化运营的智能体租用 + 计量计费平台」。评审完成后，产品负责人连续澄清了以下口径（**用户明确，优先级高于任何文档推断**）：

| # | 口径 | 确认轮次 |
|---|---|---|
| P-1 | **AgentPanel 是「后台管理 + 业务支撑」平台，以独立插件方式工作**，后续要集成信息化模块（CRM、HR、财务等）。不是「智能体租用/计费平台」——那只是 `harness` + `customer` 一条业务线 | 定位澄清 |
| P-2 | **`customer` 表 = 外部客户/消费者（C 端）**，**`user` 表 = 企业内部用户（员工）**，两者是不同主体不可混用 | 主体域澄清 |
| P-3 | 系统本就是三域建模：`OwnerType` = `CUS` / `USR`（叠加 RBAC `DataScope`）/ `ORG`；`identity_link` 是 CUS↔USR 唯一桥且禁止静默绑定；`department` 与 `customer_organization` 是两棵不同的树 | 主体域核实 |
| P-4 | **企业内部信息化模块（CRM/财务/进销存/HR/审批）归 USR 域按部门授权；Harness 商业化归 CUS 域**。HR 应建在 `user` + `department` 之上 | 主体域结论 |
| P-5 | **CRM 客户用「客户分类」容纳来源**（平台注册 / 客户介绍 / 拜访），不按 B/C 拆表；来源与「个人 vs 企业」主体性质是正交维度 | 客户分类澄清 |
| P-6 | **客户与公司绑定，但不需要强绑定**（弱关联） | 公司关联口径 |
| P-7 | **个人客户是根主体；企业客户必须由个人客户升级认证而来；直接注册企业客户必须同时填写个人客户信息** | 认证流程口径 |

首轮评审时这些输入尚不存在，因此它**不是判断失误，而是评审前提缺失**。但前提一旦变化，结论必须重算——这正是本次复审的合法性来源。

- **范围内**：PRD v1.0 全文、首轮评审报告 28 条问题（7 Blocker / 14 Major / 7 Minor）、两份文档的方法论与适用范围。

## 1. 复审结论

### 1.1 双结论与首轮对比

| 项 | 首轮结论 | 复审结论 |
|---|---|---|
| PRD v1.0 文档 | **有条件通过**：可作内部对齐基线，不得对外或作为上线验收依据 | **不通过**：定位错误导致全文需求层级错位，须重构为《平台 PRD》+《插件 PRD》两层；v1.0 改名降级为《Harness 商业化插件 PRD》 |
| 产品发布 / 商业化验收 | **不通过**（B-01~B-07 未闭环） | **该结论不适用**：首轮以「商业化计费平台」为既定产品目标，而该目标已被 P-1 推翻。不能用一个不存在的目标去判定发布条件 |
| 平台能力 | 未评估 | **不具备集成新信息化模块的需求基线**：平台层需求（插件契约、主体域、主数据、权限、事件规范、集成规范）在 v1.0 中为零 |
| 首轮评审报告自身 | 未列入评审对象 | **存在方法论缺陷**（NB-08）：缺「评审前提」章节，结论在错误前提下自洽 |

一句话：**首轮把审查做对了，但审错了对象；技术侧的发现依然有效，产品侧的结论整体失效。**

### 1.2 同一份文档、两种视角的评分

| 维度 | 作为《Harness 插件 PRD》（首轮口径） | 作为《平台 PRD》（正确口径） |
|---|---|---|
| 完整性 | 3.0 | **1.0**（平台层六个必含章节全缺） |
| 一致性 | 2.0 | **1.5**（§3.2 非目标与集成路线图互斥，见 NB-06） |
| 可追溯性 | 1.5 | 1.5（不变，且丢失范围被低估，见 NB-07） |
| 可验证性 | 2.0 | 2.0（技术指标仍有效，但业务验收方向错误） |
| 可实现性 | 4.0 | **3.0**（技术实现可信，但平台装配无验收） |
| 安全合规 | 2.0 | **1.5**（新增企业认证资料的个人信息合规缺口） |

结论：**v1.0 作为插件层文档质量基本不变（2.6），作为平台层文档则明显不合格**。因此整改不是「把 488 行改得更好」，而是「把它放回正确的层级，再补一份新的」。

## 3. 新增平台级问题（NB-01~NB-08）

### NB-01（Blocker）产品定位错误，全文需求层级整体错位

- **证据**：v1.0 §1.1 定位、§1.2 背景五问、§1.3 G1~G6、§1.4 PC-1~PC-6、§2 角色与 S1~S6、§3.1 范围、§4 架构视图、§5 FR-01~15、§6 流程、§9 验收、§10 里程碑——全部围绕「桌面端注册→租约→网关计量→会员充值」这一条 Harness 链路。对照 P-1 与仓库事实：24 个插件、8 个启用，`web/src/views/` 与插件几乎一一对应；`finance` 已有 35 router / 15 model / 9 service / 8 大菜单组与业财事件凭证生成，**是完整实现只是开关关着**；HR 无独立插件。
- **影响**：488 行里没有一条平台层需求。照此排期只会继续在 Harness 线加码，不会推进 CRM/HR/财务集成；首轮评审的 W1~W4 整改顺序同样把资源导向支付打通，方向错误。
- **建议**：① 新建《平台 PRD》（底座能力、插件契约、主数据/主体域、权限、事件与服务注册、集成规范六大必含章节）；② v1.0 改名《Harness 商业化插件 PRD》并降级；③ 其余业务线各出《插件 PRD》；④ 首轮评审报告加「前提已变更」提示，避免被继续引用。
- **验收**：平台 PRD 含上述六章，且**不含任何具体插件的业务规则**；任一插件的业务规则可在不改平台 PRD 的前提下独立修订。

### NB-02（Blocker）文档层级缺失，插件契约未进入需求

- **证据**：`base/common/plugin_manager.py` 的契约已相当完整——`manifest.json` 声明 routes/models/schemas/dependencies/menus/permissions；`enable_plugin` 校验依赖；`load_enabled_plugins` 用 DFS 拓扑排序；启停自动注入/清理菜单与权限；支持 zip/目录安装卸载与 `on_enable/on_disable/on_startup/on_shutdown/on_uninstall` 生命周期；`base/common/router.py:25` 按 `is_installed && is_enabled` 门控路由。而 v1.0 §4 只画了 L1/L2/L3 三进程部署分层，**全文未出现插件装配机制**。
- **影响**：这是平台最值钱的资产，却没有任何需求定义。集成新模块时无规范可依，只能照抄现有插件。
- **建议**：平台 PRD 新增「插件契约」一等章节：manifest 字段规范、依赖拓扑与环检测、菜单/权限注入语义、生命周期钩子触发时机、启停对运行中请求的影响、禁用插件的数据保留与迁移策略、跨插件调用约束（见 NB-05）。
- **验收**：按文档新增一个示例插件，可独立安装/启用/禁用/卸载且不修改任何 `base/core` 或 `base/start.py` 文件。

### NB-03（Blocker）主体域与权限模型缺失

- **证据**：`base/common/authz/constants.py` 已定义三域 `OwnerType`；`base/plugins/customer/models/identity_link.py` 双向唯一、只允许「提示→主动确认→验证」建立（R-14）、`customer.system_user_id` 已废弃只读；`packages/common/models/customer_organization.py` 属 CUS 域；`base/core/dept/models/department.py` 与 `base/core/users/models/users.py` 属 USR 域，`base/common/authz/scope.py` 已实现 `DataScope` 四档。v1.0 §2 把「终端客户」与「运营管理员」并列却未写域边界，§8.1 把 `customer` 与 `user` 混列在一个实体清单，§8.2 术语表无 CUS/USR/ORG。
- **影响**：不写死边界，后续每个模块都会各自造一套 owner 逻辑——这正是 CRM 客户主数据复用 C 端 `customer` 表的成因（见 NB-04）。
- **建议**：把 §5 已确认口径固化为平台 PRD 硬约束 C-01~C-07（见 §5 表）。
- **验收**：平台 PRD 明确「信息化模块归 USR 域按部门授权 / Harness 商业化归 CUS 域」，且有反例检查清单（如禁止在 HR 模块引用 `customer` 表）。

### NB-04（Blocker）CRM 客户主数据语义结与升级认证规则全缺

- **证据**：CRM **无独立客户实体**——`crm_contact` / `crm_opportunity` / `crm_follow_up_task` / `crm_lead.customer_id` 均为裸 `customer_id` BigInt，指向 C 端 `customer`；`crm/services/contact_service.py:14`、`opportunity_service.py:24` 直接 import `Customer`；`lead_service.py:93-116` 线索转化时 `Customer.create(...)` **自动创建消费者账号**；`crm/manifest.json` 依赖 `customer`。影响面不止 CRM：`finance/models/receivable.py:17/49`、`finance/models/tax.py:30`、`sales/models/order.py:91` 四处 `ForeignKeyField("models.Customer")` 同样指向 C 端表。运行时 PostgreSQL 只读核验共 **215 张表**，`company` 匹配 **0**（`customer*` 6 张、`crm*` 9 张、`department` 1 张）——**代码与运行时库均不存在 company 表**，后台「公司列表」实为 `department.type=company` 节点（`GET /companies`）。
- **好消息（可沿用）**：财务三处已是 `on_delete=SET_NULL, null=True` + `customer_name` / `customer_tax_id` 冗余快照，天然符合 P-6 弱绑定与「历史不回写」；`sales.CustomerOrder` 却是 `on_delete=CASCADE`（删客户连带删订单），业财上不可接受，须改 SET_NULL + 快照；`purchase/models/supplier.py` 已有完整企业字段模板（`tax_id`/开户行/账号/`credit_limit`/`payment_term`/`SupplierType` 枚举 + `get_label()`）。
- **影响**：按 P-5/P-6/P-7 集成财务应收与开票前必卡——B2B 企业名称、统一社会信用代码、开票抬头、客户分级、多联系人层级无处安放；「客户介绍/拜访」来的线索会被凭空开一个平台账号。
- **建议**：① 新建 `crm_customer`（个人根主体）与 `company`（企业认证档案，`credit_code` 唯一）；② 个人↔企业多对多关联 + 角色（法人/管理员/经办人）；③ 认证状态机 `none/pending/approved/rejected/expired/revoked`，USR 域后台按 `data_scope` 审核；④ 两条入口（个人注册 / 直接注册企业+填个人信息）统一收敛为「先建个人客户 → 再发起同一条认证流程」；⑤ 结算/开票主体由**单据显式选择**，开专票硬条件 = 企业 `approved` + 税号非空；⑥ 改 6 处引用、修 `CustomerOrder` 的 CASCADE、去掉 `crm→customer` 依赖、做存量数据迁移；⑦ 线索转化禁止对非「平台注册」来源自动 `Customer.create(...)`。
- **验收**：业务用例覆盖个人升级为企业、直接注册企业（个人信息必填）、同一 `credit_code` 重复认证被拒、认证未通过时禁开专票、升级前单据名称/税号快照不被回写。

### NB-05（Blocker）「以独立插件方式工作」名不副实

- **证据**：独立性目前只到**路由 / 模型 / 菜单**层。`base/start.py:26` 模块顶层硬 import harness 的 gateway_config；定时任务硬引用 `sales.OrderService`、`customer.CustomerMembership`、`llm.LLMUsageRecord`；`base/plugins/finance/services/finance_integration_service.py` 靠 `try/except ImportError` + `FINANCE_AVAILABLE` 兜底跨插件引用。
- **影响**：关掉插件后路由是没了，主进程启动或定时任务仍可能报错；每集成一个新模块都要动 `start.py`，与 P-1 直接冲突。
- **建议**：核心对插件的硬引用改为服务注册 / 事件契约；约定跨插件调用只允许事件或显式服务接口，禁止 `base/core` 层 import 插件实现；定时任务改为订阅事件或按插件注册表动态装载。
- **验收**：逐个关闭 8 个已启用插件中的非依赖链底层插件，主进程启动 + 定时任务执行均不报错。

### NB-06（Blocker）§3.2 非目标清单与集成路线图互斥

- **证据**：v1.0 §3.2 第 3 条「**不拆数据库、不改表结构、不迁历史数据**」、第 5 条「不做同一时刻双写」等，均引自 `l3-service-split/spec.md §0.2` 与 `harness-orchestration-split/spec.md`——它们是 **L3 服务拆分专项的技术约束**，被误提升为产品级「明确非目标」。而 P-1 的路线图需要新建 `crm_customer` / `company` 表、改 6 处 FK、做存量数据迁移、集成 HR 与财务。
- **影响**：把专项约束当成平台非目标，会在需求层直接阻塞集成工作；两份文档出现「承诺—路线」互斥，属于新的内部矛盾（首轮只发现了 PC/FR 之间的冲突，未发现这一处）。
- **建议**：拆成两张表——「L3 拆分专项约束（仅适用于该专项、有明确失效条件）」与「平台产品非目标」；平台层另行定义非目标，且不得包含任何会阻塞新建主数据或迁移的条款。
- **验收**：平台 PRD 非目标清单中无阻塞主数据建设/迁移的条款；专项约束标注适用范围与失效条件。

### NB-07（Major）丢失 PRD 的范围被低估，原 PRD 主角完全未覆盖

- **证据**：全库 `PRD §` / `docs/` 注释溯源显示，丢失文档至少含《用户侧智能体设计流PRD.md》`§3.2(D1~D8)`、`§3.3(L1~L10)`、`§7.1`（归属与隔离、强制规则 1~4）、`§7.2`（模型/知识库/工具/子Agent/节点类型授权矩阵）、`§7.3`（画布页问题面板），另有独立《资源授权管理 PRD》`§6.1/§6.3/§6.4` 与 `docs/arch/02`~`06`（领域模型、接口契约、防越权四层、架构自检）。`base/common/authz/` 整套模块与未启用的 `agent` 插件（用户侧工作流 dry-run / HITL / 执行事件）才是原 PRD 主体，v1.0 与首轮评审**一行未覆盖**。
- **影响**：重建策略若继续沿 Harness 线扩写，会持续遗漏原 PRD 主角。
- **建议**：先产出《原 PRD 章节大纲反推表》（按 § 编号列出可反推程度与代码依据），作为平台/插件 PRD 重建的输入，再补平台层。
- **验收**：大纲覆盖代码注释中出现的所有 § 编号，逐条标注「可反推 / 部分 / 不可反推」，不可反推项列入待签字清单。

### NB-08（Major）首轮评审缺「评审前提」门禁

- **证据**：首轮 §1 的三条核心判断、§6.1 决议「产品发布/商业化验收不通过」、§6.3 W1「回答商业化与否」全部以 §1.1 定位为既定前提；首轮 §7 备查事实中不含「产品定位及其确认人」这一项。
- **影响**：结论在错误前提下自洽，容易误导排期（把资源投向支付打通而非平台化重构），且前提变化时无强制复审机制。
- **建议**：评审模板新增「评审前提」章节，记录产品定位、适用范围、确认人与确认日期；前提变更即触发复审并撤销受影响结论；评审报告结论须标注适用层级（平台级 / 插件级）。
- **验收**：后续所有评审报告含「评审前提」章节，且结论逐条标注层级。
