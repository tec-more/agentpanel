## 1. 评审结论（摘要）

这份重建版 PRD 解决了「需求散落、无法追溯」的问题：把 12 份 spec、3 份架构文档、20+ 份运维报告中的约束统一编号，首次区分「已交付 / 观察期 / 未交付 / 形同虚设」，并显式列出 6 条不可协商的产品契约（PC-1~PC-6）。作为**内部技术对齐基线**，它是目前仓库里最完整的一份需求文档。

但它**还不是一份合格的产品 PRD**，更谈不上可据此发布。核心判断有三条：

1. **需求基线断了根**。原 PRD（`docs/用户侧智能体设计流PRD.md`）及 `docs/arch/*` 全缺，身份关联 L1~L10、脱敏 D1~D8 只能从代码注释反推，L2/L4 完全空白。代码里还留着指向不存在文档的溯源注释。这意味着**没有任何一条需求能被「签字确认」**，所有验收都退化成「以代码现状为准」——即实现即需求，这是需求管理的反向。
2. **商业闭环是断的**。产品定位写的是「可商业化运营的租用 + 计量计费平台」，但三个支付插件全部 `is_installed=false / is_enabled=false`，路由不挂载，回调不可达；`config.conf` 里 `enabled=true` 是无人读取的假开关；`payment_service.py` 还留着「从配置文件加载支付配置」的 TODO。也就是说 **用户能注册、能用、能被计量，但付不了钱**。
3. **产品契约内部自相矛盾**。PC-3 承诺「不让用户欠费跑模型」，但 FR-06 明写「无 QuotaPlan 时 `limit=0` = 不计量不拦截」——新注册客户可无限免费使用；PC-1 承诺「网关是唯一计费权威（流量必须且只能经网关）」，但 PC-6 同时承认「不保证客户端不出网」，且 `web_fetch`/`web_search` 实测可绕网关直连。**权威账的前提不成立时，权威账就不权威**。

一句话：**这是一份优秀的「as-built 系统说明」，但作为「to-be 产品需求」它缺目标、缺口径、缺验收、缺商业闭环。**

## 2. 阻塞级问题（Blocker）

### B-01 需求基线不可追溯，C 级条款占关键路径

- **证据**：全仓无 `docs/`、无任何 PRD 文件；`base/plugins/customer/services/identity_service.py:5-8` 溯源 `docs/用户侧智能体设计流PRD.md §3.2/§3.3` 与 `docs/arch/04/05/06-*.md`；历史会话检索无留存。PRD §5 FR-02 中 **L2、L4 无法反推**，D1~D8 仅 4 条可推断。
- **影响**：身份关联是涉及「同一自然人双主体」的敏感功能，其提示频率、解绑冷却、验证锁定、审计留存都是合规相关约束。以反推条款做验收等于没有验收；一旦发生客诉或数据争议，无据可依。
- **建议**：① 优先从备份 / 历史 git 对象 / 外部文档库找回原文；② 找不回则由产品负责人对 FR-02 逐条**追认或重写并签字**，明确标注「本版起生效，历史实现按新条款复核」；③ 同步清理或改写代码中指向不存在文档的溯源注释；④ 把 `docs/` 纳入版本库并设为 PRD 唯一存放位置。
- **验收**：FR-02 十条 + D1~D8 全部有签字版本，且代码行为与新条款逐条比对通过。

### B-02 商业闭环断裂：支付链路完全不可达

- **证据**：`base/plugins/qixiang_pay/manifest.json`、`wechat_pay/manifest.json`、`alipay/manifest.json` 三者均 `"is_installed": false, "is_enabled": false`；`base/common/router.py:25` 按 `is_installed && is_enabled` 门控路由；`config.conf [qixiang_pay] enabled=true` 在 `setting.py` 中无对应属性、服务代码不读；`[aif2f] enabled=true` 全库零读取点；`payment_service.py:24` 保留 `# TODO: 从配置文件或数据库加载支付配置`。
- **影响**：PRD §1.1 定位与 G4（自助充值）无法成立；FR-08 标注「未打通」但优先级却是 P0 —— P0 需求未实现意味着产品不可发布。支付回调不通还可能导致「已付款未到账」的资损风险（一旦有人手工启用路由而回调验签未联调）。
- **建议**：明确二选一并写进 PRD：
  - **方案 A（本期商业化）**：启用支付插件 → 补全配置项读取 → 回调验签与幂等 → 端到端联调（含沙箱支付、订单过期、重复回调、金额篡改）→ 补业务验收用例。
  - **方案 B（本期不商业化）**：把「会员/订单/支付」整体降级为 P2 并从 §1.1 定位中删除「商业化/计费」措辞，改成「内部计量与配额管控平台」，同时下调 G4。
  - 无论哪种，清理 `config.conf` 中无人读取的 `enabled` 开关，避免「配置显示启用、实际未启用」的运维误导。
- **验收**：至少一条真实（或沙箱）支付 → 回调 → 时长/额度增加 → 租约恢复可用的端到端用例。

### B-03 计费口径未收敛，权威账缺少门禁

- **证据**：PRD PC-1 声明 `usage_record(source=gateway)` 为唯一权威账；但 `HarnessStep`（证据账）与 `LLMUsageRecord`（遗留账）并存；`reports/architecture/target-architecture-local-agent.md §9` 将「停写 `LLMUsageRecord`、历史回填、P6 三方对账门禁」列为**未交付**；`as-built-architecture-2026-11-09.md §9.6` 记录 `reconcile_in_orchestration=false`；重复结算 / `used` 多加 / 预占悬挂仍需每日 **人工 G1 抽查**，Prometheus 判不了。
- **影响**：三套账同时存在且无自动门禁，意味着「按真实用量准确计费」（G2）无法被证明。对账设计是「只发现不改账」，发现差异后靠人工，既漏检又难追责。
- **建议**：① 明确 `LLMUsageRecord` 停写时间表与历史回填方案，或书面声明该表不参与任何计费；② 把 P6 三方对账门禁从「未交付」提为发布阻塞项；③ 把每日 G1 抽查自动化为可告警指标；④ 在 PRD §8.2 增加「任何新增用量写入点必须标注 source 且不参与计费」的约束。
- **验收**：同一 run 在网关账 / 证据账 / 遗留账之间的比对结果可自动产出，差异超阈值即阻断发布。

### B-04 产品契约内部矛盾：PC-3 与 FR-06 冲突

- **证据**：PC-3「不让用户欠费跑模型」；FR-06「无 `QuotaPlan` 的 customer → `resolve_plan=None` → `limit=0.0`，仅当 `owner_limit>0` 才施加账户级限制，故 **0 = 不计量不拦截**」（`.workbuddy/memory/2026-11-10.md:251-252`、`customer-auth-e2e-2026-11-11.md:98-100`）。E2E 报告把「无 QuotaPlan 不拦截」列为遗留而非缺陷。
- **影响**：新注册客户默认无限免费使用，与「租用 + 计费」定位和 PC-3 直接冲突；等价于把配额的生效前提交给了「运营必须记得给每个客户绑套餐」这一人工动作，没有任何兜底。这是产品级资损口子，不是技术细节。
- **建议**：由产品定 Q4 —— `limit=0` 应解释为「零额度（不可用）」还是「不限额度（不拦截）」。若选前者，需默认套餐兜底 + 存量客户回填 + 未绑套餐用户的明确提示文案；若选后者，必须在 PRD 中显式写成「未配置套餐的客户不计费」，并同步改写 PC-3 与 §1.3 G3。二者不可含糊并存。
- **验收**：新建未绑套餐客户发起模型调用，结果符合产品定义且有自动化用例覆盖。

### B-05 PRD 结构性缺失：无成功指标、无业务验收、无版本规划

- **证据**：PRD §1.3 的 G1~G6 是本次反推的建议稿（C 级），原文档与现存 spec 中**没有任何商业指标**；§9 的 215 断言 / 16 / 20 全部是技术与接口断言；全文无用户故事、无原型、无异常分支文案、无里程碑排期（只有观察期）、无责任人、无优先级排序依据。
- **影响**：无法判断「做完了没有」，无法做版本取舍，无法做上线/回滚决策。当前 PRD 更接近 as-built 系统说明而非 to-be 需求文档。
- **建议**：补齐五件：① 可量化的成功指标（注册转化、付费转化、计费准确率、SLA）；② 业务验收矩阵（Given/When/Then，至少覆盖注册默认额度、计量扣减、会员折扣实付、越额拦截、充值到账、退款/重复回调）；③ 版本规划（本期 / 下期 / 不做）；④ 每条 FR 的负责人与验收人；⑤ 核心异常分支的用户可见文案。
- **验收**：§9 出现非接口类业务用例，且每条 P0 需求有对应的业务验收项。

### B-06 凭据明文存放，且配置含真实生产值

- **证据**：`config.conf` 明文保存支付商户密钥、SMTP 邮箱口令、`[auth] secret_key`、Redis 与 Qdrant 口令、数据库连接口令；`config.conf` 位于工作区且已被多处文档引用；`.workbuddy/memory/2026-11-10.md:231` 记录「硬编码 SECRET_KEY 已改为外置」，但外置后仍在同一明文文件；PRD §10 也把「读取并输出 config.conf 敏感值」列为观察期禁止项，说明团队已知风险。
- **影响**：一旦仓库 / 备份 / 日志外泄即全量凭据泄露；支付商户密钥可直接造成资损；且密钥轮换无流程（spec 风险表已列「密钥轮换窗口」）。
- **建议**：① 立即轮换所有已出现在明文配置中的凭据（**本次评审未记录任何取值**）；② 改为环境变量 / 密钥管理注入，`config.conf` 只留占位；③ 确认 `.gitignore` 覆盖与历史提交中是否已入库，若已入库需清理历史；④ 在 PRD NFR 中补「密钥不得入库、轮换周期、审计要求」。
- **验收**：配置中无真实凭据值；有轮换演练记录；`git log -p` 中无密钥残留。

### B-07 计量权威性前提不成立：出网可绕过网关

- **证据**：PC-1「模型流量必须且只能经网关」；PC-6「不保证客户端完全不出网」；`reports/ops/l3-split-acceptance.md:104-106` 与 `shared-upstream-client/spec.md §7` 记录 `web_fetch`/`web_search` 可绕网关直连（Linux 实测 example.com 返回 200），`tool_denylist` 只是策略快照而非执行边界；`harness-egress-policy/spec.md §1` 明确「不提供真实出网阻断」且「未验证 dsh 侧效果」。
- **影响**：客户端可直接用真实上游地址发起模型调用（或至少证明服务端无法阻止），则「按真实用量计费」这一产品承诺在技术上不可验证。PRD 同时写「唯一权威账」和「无法保证流量都过网关」，是逻辑上不能并存的两句话。
- **建议**：产品层面明确边界（Q8）：① 若接受，则把 PC-1 改写为「经网关的流量以网关账为权威，绕过网关的流量不在计费范围，且平台不承诺其安全与计量」，并在用户协议中披露；② 若不接受，须在发布前给出强制手段（客户端网络策略 / 工具禁用 / 进程级出网管控）并做真实出网验证。当前「只说清楚不阻断」不应与「可商业化计费」并列出现在同一版 PRD。
- **验收**：有真实出网阻断验证报告，或有产品签字接受该边界的书面记录。
