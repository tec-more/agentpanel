## 1. 引言

### 1.1 编写目的

本文档定义 AgentPanel **平台层**的产品需求，用于：① 统一产品负责人、架构、开发、测试对平台边界的理解；② 为后续集成信息化模块提供可装配、可验收的需求基线；③ 为需求排期提供可复算的评级与价值依据。

v1.0 因定位错误（把 `harness` + `customer` 一条业务线当成整个产品）被复审判定「不通过，须重构」。本版不修订 v1.0 正文，而是按正确层级重建，并保留 v1.0 作为历史记录。

### 1.2 适用范围与读者

| 读者 | 关注章节 |
|---|---|
| 产品负责人 | §2 定位与目标、§5 评级方法、§14 总表、§17 待决清单、§18 DoD |
| 架构 / 开发 | §4 总体模型、§6~§12 需求与验收、§11 数据需求 |
| 测试 | 各需求「验收标准」、§15 追踪矩阵 |

范围外：插件内部业务规则、Harness 商业化细节、L3 服务拆分专项技术约束、灰度观察期结论。

### 1.3 术语与主体域定义

| 术语 | 定义 | 依据 |
|---|---|---|
| **CUS 域** | 外部消费者主体域，主表 `customer`（openid/unionid/会员小时数/配额），入口为桌面客户端 | `base/common/authz/constants.py`、C-03 |
| **USR 域** | 企业内部员工主体域，主表 `user` + `department` 树，入口为 Web 后台，叠加 RBAC `DataScope` | `base/core/users/models/users.py`、C-03/C-05 |

| **插件** | 以 `manifest.json` 声明 routes / models / schemas / dependencies / menus / permissions，由 `plugin_manager.py` 装配的独立业务单元 | C-07 |
| **平台契约** | 适用于所有插件、且不因任一插件业务规则变更而修改的需求 | C-01/C-02 |
| **弱绑定** | 归属/统计用关联：可空、不建 FK、不 CASCADE、不唯一、可改绑、不回写历史单据 | C-09 |
| **升级认证** | 个人客户发起企业认证，通过后获得以企业主体结算/开票的资格 | C-10/C-12 |

### 1.5 文档约定

### 2.3 产品定位（C-01，硬约束）

> **AgentPanel 是「后台管理 + 业务支撑」平台，以独立插件方式工作，后续集成 CRM、HR、财务等信息化模块。`harness` + `customer` 只是一条业务线，不得据此定义平台定位。**

平台只负责：插件装配、主体域与权限、主数据契约、事件与服务注册、配置与凭据治理、审计与合规、集成规范。具体业务规则一律由插件 PRD 承载。

## 5. 需求评级与价值评定方法

> 本章是本文档的评定依据。**所有分数可复算**，不接受「拍脑袋标 P0」。价值评定回答「值不值得做」，评级回答「不做会不会阻断」，两者独立，互不换算。

### 5.1 价值评定模型（五维加权）

| 维度 | 符号 | 权重 | 1 分锚点 | 3 分锚点 | 5 分锚点 |
|---|---|---|---|---|---|
| 业务价值 | V1 | 25% | 无直接经营影响 | 提升内部效率或支撑单模块上线 | 直接决定能否开展营收 / 结算 / 合规业务 |
| 用户价值 | V2 | 15% | 仅开发运维可见 | 改善一类后台角色日常操作 | 影响全部后台角色或外部客户核心流程 |
| 平台战略价值 | V3 | 25% | 局部优化 | 被 2 个以上模块复用 | 所有后续集成的前置条件 / 平台契约 |
| 风险规避 | V4 | 15% | 无风险敞口 | 存在数据或权限隐患 | 明文凭据、越权、税务合规、数据丢失等红线 |
| 本期目标对齐 | V5 | 20% | 与本期目标无关 | 间接支撑 | 本期核心交付物 |

**计算式**：`V = 0.25·V1 + 0.15·V2 + 0.25·V3 + 0.15·V4 + 0.20·V5`（各维度 1~5 整数，V 保留两位小数）

**价值等级**：`A ≥ 4.20`｜`B 3.40~4.19`｜`C 2.60~3.39`｜`D < 2.60`

### 5.2 实现代价与置信度

| 符号 | 含义 | 取值 |
|---|---|---|
| E | 实现代价 | 1 = 仅文档/配置；2 = 单插件内小改；3 = 单模块改造含表结构；4 = 跨多模块 + 数据迁移；5 = 平台级重构 + 全量回归 |
| κ | 置信度系数，由证据等级映射 | A = 1.00；B = 0.85；C = 0.65 |

### 5.3 需求评级（阻断性判定）

| 评级 | 判定条件（满足任一） | 范围语义 |
|---|---|---|
| **P0 必须** | 不做则本期目标不可达；触发安全/合规/数据丢失红线；为全部后续工作的硬前置；复审已判定 Blocker 且层级归平台 | 本期必须交付，缺失即不定稿 |
| **P1 应该** | 显著影响效率或质量，但存在临时绕行方案；或为 P0 的规模化前提 | 本期应交付，可排后 |
| **P2 可以** | 改善型，延后不影响本期目标；或依赖未决口径 | 下期考虑 |
| **P3 暂缓** | 目标未确认、投入大且收益不确定 | 不进入本期排期 |

**一票规则（覆盖上表，须在总表备注列标注）**

| 规则 | 内容 |
|---|---|
| R1 | V4 = 5 且存在未修复的实现缺口 → 强制 P0 |
| R2 | 被 ≥ 2 条 P0/P1 需求声明为硬依赖 → 评级不低于 P1 |
| R3 | 证据等级 C 且对应待决问题未签字 → 评级不高于 P2、MoSCoW 记 `W`、状态标「暂缓排期」 |
| R4 | 前提（评审前提章节任一项）变更 → 受影响需求评级作废并重评 |

### 5.4 性价比指数（用途边界）

`PI = V × κ / E`，保留两位小数。

- **用途**：同一评级内的实施顺序排序、识别「速赢」（高 PI）与「重点投入」（高 V 高 E）；
- **不得用于**直接决定 P0~P3。理由：平台契约与主数据改造往往价值高、代价也高，若由 PI 单独定级会被系统性排后，与本期目标相悖。
- 本版中 `PLAT-01`（V 4.15 / E 1 / PI 4.15）为最高速赢，`MD-01`（V 4.55 / E 4 / PI 1.14）为最高价值重点投入，二者同为 P0。

### 5.5 本期范围（MoSCoW）

`M` Must have｜`S` Should have｜`C` Could have｜`W` Won't have（本期不做）。R3 命中项一律 `W`。
