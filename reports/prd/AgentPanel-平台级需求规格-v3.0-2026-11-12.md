## 1. 引言

### 1.1 编写目的

从产品目标出发，正向定义 AgentPanel 作为平台**必须提供的能力、约束与质量属性**，形成一份与历史需求无任何继承关系的干净基线，供平台级评审、架构设计与后续插件级需求推导使用。

### 1.2 适用范围

范围内：跨插件统一生效的契约、能力域、质量属性与治理规则。
范围外：任一具体插件的业务规则、字段、流程、状态机与计算口径；具体技术选型与实现方案；商业化目标；L3 服务拆分专项技术约束。

### 1.3 平台级判定规则（本版核心）

一条需求**同时满足以下三条**才属于平台级：

| # | 条件 |
|---|---|
| J1 | 对**两个及以上**插件或业务模块统一生效，或定义了所有模块都必须遵守的边界 |
| J2 | 不含任一具体业务实体的字段、业务流程、状态机、单据规则或计算口径 |
| J3 | 任一插件的业务规则变更时，本需求**无需修改** |

**判定示例（用于校准，不构成需求）**

| 表述 | 判定 | 理由 |
|---|---|---|
| 「跨模块共享实体的归属关联不得级联删除历史单据」 | **平台级** | J1 全模块、J2 无具体实体、J3 业务变更不影响 |
| 「插件启用时应注入其声明的菜单与权限」 | **平台级** | J1 全插件、J2 无业务字段、J3 成立 |
| 「个人客户升级企业认证需审核」 | 插件级 | 违反 J2（具体业务流程与状态机） |
| 「开专票须企业已认证且税号非空」 | 插件级 | 违反 J2（单据规则） |
| 「客户来源含平台注册/客户介绍/拜访」 | 插件级 | 违反 J2（业务分类字典） |
| 「会员等级按 Fibonacci 序列」 | 插件级 | 违反 J1/J2 |
| 「网关租约 TTL 900s」 | 插件级 | 违反 J1（单一插件） |

**明确排除清单（属插件级，本版不定义）**：客户分类与来源、企业认证与升级、开票与结算主体、线索转化、员工档案与组织架构业务字段、会员与计费口径、租约与出网策略、审批流与单据状态。这些口径此前已由产品负责人确认过，但**属于插件级需求内容**，本版只保留其存在性提示，不写入需求条目（详见 §6 与配套评审报告）。

### 1.4 术语

| 术语 | 定义 |
|---|---|
| 平台级需求 | 满足 §1.3 J1~J3 的需求 |
| 插件级需求 | 描述某一插件/模块业务规则的需求，由各插件 PRD 承载 |
| 能力域 | 从产品目标分解出的一组同类平台能力，本版共 8 个（CA-1~CA-8） |
| 推导链 | `目标 Gx → 能力域 CA-y → 需求 PLR-zz`，本版需求的唯一来源形式 |
| 主体域 | 平台对主体归属的分类契约（外部消费者域 / 企业内部用户域 / 客户域组织维度） |
| 弱引用 | 不依赖数据库引用完整性、不级联删除、以快照固化历史的跨模块关联方式 |

### 1.5 文档约定

- 编号：`PLR-xx` 平台级需求 / `AC-PLR-xx-n` 验收标准 / `Gx` 目标 / `CA-y` 能力域。
- 规范强度：【必须】不做即不通过；【应】默认要求，例外须书面说明；【可】可选；【不得】禁止。
- 证据等级：A = 产品负责人明确或代码/运行时库可证；B = 架构/spec 文档明确；C = 推断或依赖未决假设。
- 状态：`待签字` / `待定稿` / `暂缓排期`。

## 4. 需求评级与价值评定方法

> **方法论沿用，条目与分数全新**。评级体系属于文档规范，不构成「需求继承」；本版 25 条需求的 V1~V5、E、κ、PI 全部重新打分，与修改前任何条目的分数无对应关系。

### 4.1 价值分与价值等级

`V = 0.25·V1 + 0.15·V2 + 0.25·V3 + 0.15·V4 + 0.20·V5`

| 维度 | 权重 | 1 分 | 5 分 |
|---|---|---|---|
| V1 业务价值 | 25% | 无直接经营影响 | 直接决定结算/合规业务能否开展 |
| V2 用户价值 | 15% | 仅开发运维可见 | 影响全部后台角色 |
| V3 平台战略价值 | 25% | 局部优化 | 所有后续集成的前置条件 |
| V4 风险规避 | 15% | 无风险敞口 | 凭据泄露、越权、数据丢失等红线 |
| V5 本期目标对齐 | 20% | 与本期目标无关 | 本期核心交付物 |

价值等级：`A ≥ 4.20`｜`B 3.40~4.19`｜`C 2.60~3.39`｜`D < 2.60`

### 4.2 实现代价、置信度与性价比

- `E`：1 仅文档/配置｜2 单模块小改｜3 单模块改造含契约变更｜4 跨多模块改造｜5 平台级重构 + 全量回归。
- `κ`：A=1.00 / B=0.85 / C=0.65。
- `PI = V × κ / E`，**只用于同级排序与象限归类，不得决定 P0~P3**（高价值高代价的契约改造不能因 PI 低而降级）。

### 4.3 需求评级与一票规则

| 评级 | 阻断性判定 |
|---|---|
| P0 必须 | 不做则本期目标不可达 / 触发安全合规或数据丢失红线 / 为全部后续工作硬前置 |
| P1 应该 | 显著影响效率或质量，但有临时绕行方案 |
| P2 可以 | 改善型，延后不影响本期目标 |
| P3 暂缓 | 目标未确认、投入大且收益不确定 |

| 规则 | 内容 |
|---|---|
| R1 | V4 = 5 且存在未修复缺口 → 强制 P0 |
| R2 | 被 ≥ 2 条 P0/P1 声明为硬依赖 → 不低于 P1 |
| R3 | 证据 C 且前提未签字 → 不高于 P2、MoSCoW = W、暂缓排期 |
| R4 | 评审前提变更 → 受影响评级作废重评 |

### 4.4 分布与自省

| 评级 | 条数 | 占比 |
|---|---|---|
| P0 | 14 | 56.0% |
| P1 | 8 | 32.0% |
| P2 | 2 | 8.0% |
| P3 | 1 | 4.0% |

价值等级 A 4 / B 16 / C 5 / D 0；MoSCoW M 20 / S 4 / C 0 / W 1。

**自省**：P0 占比 56% 仍高于常规 ≤30%。原因是平台级需求天然多为「所有模块共用的必备契约」，缺失任一即不成平台，而非「都很紧急」。但区分度不足会削弱排期价值，已在配套评审报告登记为 Major，并给出按「是否阻断首个模块集成」二次收敛的建议；定稿目标 ≤10 条 P0。

## 5. 平台级需求（PLR-01~25）

### CA-1 插件装配与生命周期

#### PLR-01 插件声明式契约（P0 ｜ 价值 B 4.00 ｜ PI 2.00）

| 属性 | 内容 |
|---|---|
| 能力域 / 层级 | CA-1 / 平台级 |
| 推导链 | G1 → CA-1 → PLR-01 |
| 平台级判定 | J1 全插件；J2 只声明字段规范无业务字段；J3 业务变更不影响 |
| 证据 / 状态 | A / 待签字 |
| 依赖 / 范围 | — / M |

**需求描述**：【必须】每个插件以单一声明文件描述其标识、版本、依赖、路由、模型、菜单与权限集合，平台以此声明作为装配的唯一输入。【不得】允许插件以隐式约定或散落代码补充装配信息。【应】声明缺失或格式非法时拒绝装配并给出可定位的错误。

**验收标准**
- AC-PLR-01-1：删去某插件声明中的必填字段后启用，系统拒绝并指出字段位置。
- AC-PLR-01-2：同一插件的路由、菜单、权限实际注册项与声明集合完全一致，无多无少。

**价值评定**：V=4.00（B），E=2，κ=1.00，PI=2.00。装配契约是所有模块接入的前提，代价低、可一次性固化，列为速赢。

#### PLR-02 依赖解析与装配顺序（P0 ｜ 价值 B 3.75 ｜ PI 1.88）

| 属性 | 内容 |
|---|---|
| 能力域 / 层级 | CA-1 / 平台级 |
| 推导链 | G1 → CA-1 → PLR-02 |
| 平台级判定 | J1 全插件；J2 与业务无关；J3 成立 |
| 证据 / 状态 | A / 待签字 |
| 依赖 / 范围 | PLR-01 / M |

**需求描述**：【必须】平台依据声明的依赖集合计算装配顺序，并在存在环、缺失依赖或版本不兼容时拒绝启用。【必须】被依赖方未就绪时，依赖方不得进入可用状态。【应】装配顺序可查询、可复现。

**验收标准**
- AC-PLR-02-1：构造循环依赖的两个测试插件，启用被拒且错误可定位到环上的插件名。
- AC-PLR-02-2：停用底层插件时，其上层依赖方自动进入不可用状态而非抛运行时异常。

**价值评定**：V=3.75（B），E=2，κ=1.00，PI=1.88。决定多模块集成是否可控，属低成本速赢。

#### PLR-03 启停门控与菜单权限注入（P0 ｜ 价值 A 4.30 ｜ PI 2.15）

| 属性 | 内容 |
|---|---|
| 能力域 / 层级 | CA-1 / 平台级 |
| 推导链 | G1 → CA-1 → PLR-03 |
| 平台级判定 | J1 全插件；J2 只定义注入语义；J3 成立 |
| 证据 / 状态 | A / 待签字 |
| 依赖 / 范围 | PLR-01、PLR-02 / M |

**需求描述**：【必须】仅「已安装且已启用」的插件挂载路由。【必须】启用时注入其声明的菜单与权限，禁用时清理对应菜单与权限且不留残留。【不得】把「未启用导致菜单不显示」视为缺陷——这是按需装配的设计特性。【应】门控判定集中在一处，禁止各插件自行实现。

**验收标准**
- AC-PLR-03-1：四种状态组合（安装×启用）逐一验证路由可达性，仅双真时可达。
- AC-PLR-03-2：启用→禁用后，菜单与权限项数量回到基线，无孤儿记录。

**价值评定**：V=4.30（A），E=2，κ=1.00，PI=2.15。全平台装配可见性的核心，价值最高且代价低。

#### PLR-04 生命周期钩子与失败语义（P1 ｜ 价值 C 3.30 ｜ PI 1.65）

| 属性 | 内容 |
|---|---|
| 能力域 / 层级 | CA-1 / 平台级 |
| 推导链 | G1 → CA-1 → PLR-04 |
| 平台级判定 | J1 全插件；J2 不含业务动作；J3 成立 |
| 证据 / 状态 | A / 待定稿 |
| 依赖 / 范围 | PLR-01 / M |

**需求描述**：【应】平台定义启用、禁用、启动、停止、卸载五类钩子的触发时机、执行顺序与失败处理；【必须】钩子失败不得使平台进入部分装配的未知状态，须可回滚或明确标记降级。【应】钩子执行结果可查询。

**验收标准**
- AC-PLR-04-1：注入一个故意失败的启用钩子，插件状态回退且平台其余插件不受影响。
- AC-PLR-04-2：五类钩子的触发时机在文档中有明确时序说明。

**价值评定**：V=3.30（C），E=2，κ=1.00，PI=1.65。有临时绕行（人工处置），故 P1。

#### PLR-05 安装卸载与数据保留（P2 ｜ 价值 B 3.45 ｜ PI 0.98）

| 属性 | 内容 |
|---|---|
| 能力域 / 层级 | CA-1 / 平台级 |
| 推导链 | G1 → CA-1 → PLR-05 |
| 平台级判定 | J1 全插件；J2 不定义具体业务数据；J3 成立 |
| 证据 / 状态 | B / 待定稿 |
| 依赖 / 范围 | PLR-01 / S |

**需求描述**：【应】平台支持以包或目录形式安装与卸载插件；【必须】禁用插件时其业务数据默认保留，卸载与数据清除为两个独立动作且需显式确认。【应】卸载前给出受影响数据范围的提示。

**验收标准**
