# ContentOps 卡点解决报告：平台 API 可用性与 LLM 出域合规

| 项 | 内容 |
|---|---|
| 版本 | v1.1 |
| 日期 | 2026-11-17 |
| 针对卡点 | PRD v1.1 §14 的 T2（LLM 出域法务确认）、T4（5 平台 API 可用性评估） |

> **重要声明**：本报告是技术可行性调研与合规方案建议，**不构成法律意见**。法务签字、平台资质申请仍需责任方执行。文中结论用于消除"能不能做"的不确定性，让开发可以据此决策。

## 卡点 T4：5 平台官方 API 可用性评估

### 结论总表

| 平台 | 官方发布 API | 准入条件 | 判定 | 接入策略 |
|---|---|---|---|---|
| 微信公众号 | ✅ 完整（草稿+发布） | 需认证服务号/订阅号；IP 白名单；**个人主体/未认证企业 2025-07 起发布接口被回收** | 可行 | 官方 API，主力通道 |
| 微博 | ✅ 有（statuses/update） | 开发者认证（企业优）；申请 `statuses_update` 权限（默认不开放，需提交场景说明审核） | 可行 | 官方 API，需提前申请权限 |
| 抖音 | ✅ 有（内容发布能力） | 企业主体认证 + 应用审核 5–15 工作日；需官网、备案回调域名、经营范围匹配 | 有条件 | 官方 API 为主，RPA 兜底需评估 |
| 今日头条 | ⚠️ 部分 | 头条号图文发布无公开第三方入口（developer.toutiao.com 已转向小程序）；字节开放平台有视频发布 API（需申请 `toutiao.video.create`） | 部分存疑 | 图文走 RPA/草稿兜底，视频走官方 API；待实测 |
| 小红书 | ❌ 无 | 开放平台仅电商类接口；分享开放平台是"唤起 App 内发布工具"；App 端发布受设备指纹/行为图谱风控；**无第三方笔记发布 API** | 阻塞 | 见下方专项处理 |

### 关键发现

1. **微信公众号**：官方文档明确 `freepublish/submit` 等发布能力自 2025-07 起对个人主体、未认证企业账号回收。→ 必须用**已认证的企业主体账号**，且配置服务器公网 IP 白名单（动态 IP 需固定云服务器）。这与 D7 多租户并不冲突，但要求每个租户提供自己的认证账号。

2. **微博**：发布接口 `statuses/update` 存在，但权限默认不开放，需开发者认证 + 应用场景说明人工审核（1–3 工作日）。个人号仅基础权限，企业号可批量。

3. **抖音**：官方开放平台确有"内容发布"能力（第三方应用视频/图文同步发布至抖音），但应用审核材料门槛高（官网、备案域名、营业执照经营范围）。第三方群控/批量软件撞"账号健康分"红线，**不建议**。D4 已定"视频仅元信息适配、不剪视频本体"，而抖音主场景是视频——这构成一个**范围矛盾**（见下方风险）。

4. **今日头条**：调研出现冲突信息——部分资料称头条号图文无官方发布 API（`developer.toutiao.com` 重定向到小程序开放平台），另一些实战文章称头条号开放平台有"文章发布/图片上传"权限（仅认证号可开）。字节开放平台 `open.douyin.com` 确有 `toutiao.video.create` 视频发布接口。**结论：必须以实测为准**，列为待验证项，不阻塞开发（Adapter 接口预留，两种实现都留口）。

5. **小红书（阻塞，重点）**：
   - 官方开放平台 API 文档是**电商类**接口（商品、物流），不含笔记发布。
   - 分享开放平台提供的是"基于小红书 App 内发布工具"的分享 SDK，需唤起 App，由 App 完成发布——不是服务端 API。
   - 社区/问答资料一致指出：所谓 `user.notes.write` scope 不存在；Web/网页版自动化依赖登录 cookie，而《小红书用户服务协议》(2026-03-23 更新) 第 4.1 条明确禁止"通过非小红书公司开发、授权、许可的第三方软件、插件、外挂、系统登录或使用小红书平台"，账号仅限本人使用。
   - GitHub 上的小红书 MCP/Skill 驱动网页版，存在登录态泄露、封号、维护中断三重风险（某仓库 420 个 issue 中 16 个提到封号）。

### 小红书阻塞的处理方案（三选一，需决策）

| 方案 | 做法 | 优点 | 代价/风险 | 建议 |
|---|---|---|---|---|
| A. 半自动导出 | 系统完成合规+自适应，导出成品文案+图片，人工在小红书 App/网页端发布 | 100% 合规，零封号风险；符合 D1"人工确认后发"调性 | 无法一键发布，多一步人工 | **推荐** |
| B. RPA 网页自动化 | 用登录 cookie 驱动网页版自动点击发布 | 全自动 | 明确违反用户协议 4.1 条；封号、登录态泄露 | **不建议**，与 D5"允许 RPA"冲突，需收回对该平台的 RPA 授权 |
| C. 企业白名单合作 | 申请小红书品牌号/企业号白名单接入内容管理后台 | 官方合规 | 需商务合作，门槛高、周期不确定 | 作为中长期目标 |

> **建议**：对小红书采用方案 A，把它定义为"合规校验 + 内容生成 + 人工发布"通道，而非"自动发布"通道。这样既保住小红书这个阵地，又不踩协议红线，且与 D1 人工确认的产品定位一致。需要同步修订 PRD §4/§6，在平台矩阵中标注小红书的通道类型。

> **✅ 决策结果（2026-11-17 用户确认，对应 N1）**：小红书采用**半自动通道**——系统完成内容合规处理与自适应生成，输出成品；**不进行任何自动发布、不使用网页版 RPA 自动点击**；最终由人工在小红书 App/网页端点发布。收回该平台的 RPA 授权。此结论与方案 A 一致。

### 范围矛盾提示（D4 × 抖音）

D4 决定"视频仅元信息适配、不剪视频本体"，但抖音的核心内容是视频。若不做视频本体上传，抖音 Adapter 只能发图文/图文笔记，运营效果会打折。建议二选一：
- 维持 D4：抖音定位为"图文/图文笔记"通道，视频发布留给后续版本；
- 放宽 D4：抖音允许上传外部提供的成片视频（仍不做自动剪辑），仅自动化发布动作。

> **✅ 决策结果（2026-11-17 用户确认，对应 N2）**：**放宽 D4**——抖音允许上传外部提供的成片视频，系统负责合规检测、封面/标题/话题适配与自动发布，**仍不做视频自动剪辑**。需同步修订 PRD §0 的 D4 描述与 §4/§6/§15。

## 卡点 T2：LLM 出域合规方案

### 结论

**不需要等一个笼统的"法务点头"，而是把方案收敛成三个可核实的硬条件，让法务做单点确认。**

### 三个必要条件（必须同时满足）

| # | 条件 | 具体要求 | 核实方式 |
|---|---|---|---|
| C1 | 境内节点 | 选用已完成境内算法备案的国产大模型 API（通义千问/文心/豆包/混元/DeepSeek/智谱 GLM 等），数据全程不出境 | 核查厂商备案信息 + endpoint 物理区域 |
| C2 | DPA 三条款 | 与供应商签数据处理协议，明确：① 输入/输出不用于训练；② 数据传输不出境（境内节点）；③ 处理完成后按期删除（如 30 天） | 签署书面 DPA |
| C3 | PII 脱敏 | 送入模型前对内容做个人信息脱敏（手机号、身份证、客户名、合同金额等）；审计日志只记调用元数据不记正文 | 代码层脱敏钩子 + 日志审计 |

### 支持证据

- **区分网页版与 API**：主流厂商的 API 服务普遍承诺"输入输出不用于训练"，而网页版对话可能被用于改进模型。→ 必须用 API，禁止把网页版对话当 API 用。
- **数据出境判定标准**：看服务器物理位置是否在境内，不看网络路径。用 VPN/中转绕道海外不改变"数据已出境"的事实。
- **合规路径**：选国产已备案模型 = 数据全程不出境，合规成本最低。这是国内企业交付的推荐方案。海外 API（OpenAI/Anthropic）需安全评估或标准合同 + 明示同意 + 匿名化，成本高周期长。
- **反面案例**：某 SaaS 企业用海外 AI API 做邮件自动回复，未签 DPA 且未脱敏，客户合同金额随正文进入 API，被监管约谈，最终下线功能并迁移，周期 6 周。
- **行业动向**：智谱 GLM 已推出"no data retention"选项，输入与输出在处理后不存储，是目前较严格的数据隐私安排之一，可优先考虑。

### 落地到设计（不依赖法务即可先做的部分）

1. `LLMAdapter` 抽象层强制注入 `region=domestic` 约束，配置层**禁用海外 provider**（代码层硬约束，不靠人自觉）。
2. 在适配引擎入口增加 PII 脱敏钩子（`pii_scrubber`），所有送模型文本先过脱敏。
3. 审计日志只记录 model / token 数 / 耗时 / trace_id，**不记录内容正文**。
4. DPA 模板与厂商选型清单交付法务，做单点确认（不再是开放式咨询）。

### 法务单点确认清单（交给法务一页纸）

- [ ] 确认候选厂商清单（国产已备案）中至少一家可用于本项目
- [ ] 确认 DPA 三条款文本可接受
- [ ] 确认 PII 脱敏范围满足公司数据分级要求
- [ ] 确认数据留存期（建议 30 天内删除）

## 附录 A：第三方聚合发布平台调研（2026-11-17）

> 用户曾询问"有没有第三方集成发布平台"。结论：**有，但用户最终选择"系统内处理、人工发布"，不采用。** 本节留档。

### 市面主流平台

| 类别 | 代表 | 特点 |
|---|---|---|
| 商业聚合 SaaS | 蚁小二（40+ 平台，开放 API + CLI）、新榜矩阵通（API 较完整、重数据）、聚媒通（60+ 平台、环境隔离）、CreBee（API/Skill/MCP）、优采云、融媒宝、易媒助手 | 一键分发多平台，宣称带 API；实际发布多为 Cookie/RPA 驱动网页版，价格从免费 5 账号到数百元/月 |
| 开源/开发者工具 | 矩媒 MatrixMedia（GUI/CLI/HTTP API/MCP、数据本地）、unified-publish-mcp（28+ 平台、MCP 原生）、catbus（CLI 驱动 10 平台 web 端点） | 适合技术团队嵌入自动化流程，需自行维护，平台数少于商业工具 |
| iPaaS 连接器 | 集简云、数环通 | 偏流程编排与 Salesforce/办公套件连接，非专门发布中台 |

### 不采用的原因

1. **不消除风险**：第三方"一键发布"本质多为 Cookie/RPA 网页态自动化，同样违反平台协议、有封号风险，只是把风险转移给工具方。
2. **小红书无解**：第三方发小红书仍是网页自动化，违反其用户协议 4.1 条。
3. **数据经过第三方**：内容与登录态托管给外部，与本项目的租户隔离、数据不出域原则冲突。
4. **合规风向收紧**：中央网信办"清朗·整治 AI 应用乱象"已将批量发文、AI 托管水军列入处置，合规闸门应自持。
5. **用户决策**：系统只做合规处理 + 自适应，成品导出后人工发布，从根本上规避上述全部问题。

### 最终发布层架构（PRD v1.2）
系统不接任何平台 → 合规 + 自适应 → 成品导出（文案/图片/封面/成片打包）→ **人工在各平台发布** → 发布台账 + 人工回填数据。无 Adapter、无 RPA、无凭证托管、无自动数据回流。
