## 1. 为什么是「完全独立前端」

后台管理 SPA（`/panel`）面向企业内部员工（USR 域，JWT `typ=usr`），客户门户面向外部客户（CUS 域，`typ=cus`）。两者身份、可见数据、UI 完全不同，因此做成**独立 Vite 项目** `customer-portal/`：

- 独立构建入口、独立依赖、独立部署路径 `/portal/`；
- 独立 token 存储键（`cp_token`/`cp_customer`），与后台 `token`/`userInfo` 物理隔离，杜绝同浏览器串号；
- 后端服务由 `customer` 插件的 manifest 路由装配提供，**不新挂入口路由**。

## 2. 本轮交付清单

| 层 | 内容 | 落点 |
|---|---|---|
| 鉴权守卫（P0） | `require_customer`：在 `require_owner` 基础上强制 `owner_type=cus`，USR token 一律 403 | `services/cus_guard.py` |
| 自助端点 | `GET /me/profile`、`/membership`、`/orders`、`/payments`、`/organizations`，全部 `require_customer` + 按 `owner.owner_id` 过滤，不接受客户端传 ID | `api/v1/self_service_router.py` |
| 工作台端点 | `POST /workspace/compliance/check`（复用 contentops 合规引擎，平台+本租户规则）、`GET /workspace/rules` | `api/v1/workspace_router.py` |
| 独立前端 | 登录（密码/邮箱验证码）、工作台首页、合规检测、规则、资料、会员、订单、支付、组织共 9 页 | `customer-portal/` |
| 静态托管 | `/portal/*` 从 `customer-portal/dist` 提供，独立分支，不受 `/install` 跳转影响 | `base/app_wrapper.py` |
| 镜像构建 | 新增 portal-builder 阶段，产物 COPY 到 `/app/customer-portal/dist` | `deploy/app/Dockerfile` |

## 3. 安全设计（对照 C1 缺陷整改）

1. **USR 无法访问客户自助接口**：所有 `/me/*`、`/workspace/*` 依赖 `require_customer`，USR token 直接 403（回归 A2/A3）。
2. **客户无法越权读他人数据**：`owner_id` 只取 JWT `sub`，所有查询强制 `.filter(...=owner.owner_id)`，客户端传入的 `customer_id` 一律不接收；资料接口已脱敏（不返回 password/openid/unionid），回归 A5/A7 验证。
3. **合规规则按归属过滤**：`ComplianceEngine.load_rules(owner)` 加载平台级 + 本租户规则，与客户在后台看到的结果口径一致，不暴露其他租户规则。
4. 沿用双主体底座 `require_owner` + `OwnerContext`，与 contentops 的 CUS 鉴权同源。

## 4. 本地开发 / 构建

```bash
# 前端（独立项目）
cd customer-portal
npm install
npm run dev        # http://127.0.0.1:3100/portal/ ，/api 代理到后端 9998
npm run build      # 产物 customer-portal/dist，base=/portal/
```

后端需正常运行（app 9998）。开发态 Vite 已配 `/api` → `127.0.0.1:9998` 代理。

## 5. 上线部署

镜像构建已纳入客户门户（多阶段 build），重建即带上前端产物：

```bash
docker build -f deploy/app/Dockerfile -t agentpanel-app:latest .
```

构建流程：① `web-builder` 编译管理后台 → `/app/web/dist`；② `portal-builder` 编译客户门户 → `/app/customer-portal/dist`；③ 后端运行时。

**nginx 无需改动**：`deploy/nginx/conf.d/agentpanel.conf` 的 `location /` 已把所有非 `/assets`、`/metrics` 路径转发给 app，`/portal/*` 由 `app_wrapper` 的独立分支处理（WebSocket 升级头也已具备）。对外端口 `9080`。

> 若采用独立 nginx 直接托管静态产物（不经后端），需增加 `location /portal/ { alias /app/customer-portal/dist/; try_files $uri /portal/index.html; }`，并确保 `/api` 仍转发后端。当前默认走 app_wrapper，无需此配置。

## 6. 客户开通与登录

1. 管理员调用 `POST /v1/customer/auth/register`（邮箱+密码+邮箱验证码）创建客户账号；或在管理后台客户模块创建。
2. 客户访问 `http://<host>:9080/portal/`，用邮箱+密码登录，或「验证码登录」（需 `[email]` SMTP 配置可用）。
3. 登录成功后 `data.access_token`（`typ=cus`，24h）存入 `cp_token`，后续请求自动带 `Authorization: Bearer`。

> 当前无短信/微信登录（项目仅邮件验证码）；如需可后续增量，不影响本链路。

## 8. M6 可解释检测管道（过程 / 步骤 / 方法）

客户反馈原检测"只有结论、没有过程"。M6 在 `ComplianceEngine` 新增 `check_with_trace()`（**不改动**既有 `detect_text`/`aggregate`/`check_content`，M1–M5 调用零影响），客户工作台 `POST /v1/customer/workspace/compliance/check` 已改用它，前端"检测结果"下方新增"检测过程"时间线。

| 步骤 | code | 方法 | 说明 |
|---|---|---|---|
| S1 | `normalize` | NFKC 全角转半角 + 剔除零宽/不可见字符 + 折叠空白 | 反绕过：全角数字、零宽插词仍能被后续规则检出；产出归一化副本，不改原文 |
| S2 | `keyword` | 词库逐词扫描（多模式 DFA 语义） | 命中记录位置/等级/依据/建议，命中带 `layer`(L1–L4) 与 `source`(L1-关键词) |
| S3 | `regex` | 正则逐条编译执行 | 变形/组合违规（如手机号）；非法正则跳过不拖垮整次检测 |
| S4 | `disambiguation` | 白名单短语降噪（11 条，如"第一反应/最近"） | 绝对化词落在白名单内不判违规，记录抑制数 |
| S5 | `semantic` | 语义相似度 / LLM 判定 | **当前未接入模型 → status=skipped 并给出原因**，不伪装已执行；结论仅基于确定性规则，可复现 |
| S6 | `aggregate` | 最高风险等级聚合 | P0→block / P1→review / 仅P2→pass_hint / 无命中→pass，判定原因写进 detail |

响应新增字段（向后兼容，原有 `verdict`/`hits`/`has_p0` 等保留）：
- `trace`: 六步数组，每步含 `step`/`code`/`name`/`method`/`rules_scanned`/`hits_found`/`elapsed_ms`/`status`/`detail`；
- `pipeline_version`: `2.0-trace`；`rules_loaded`: 本次加载规则数；`normalized`: 是否触发归一化；`needs_review`: 是否需复核；`elapsed_ms`: 全链路耗时。

> 边界说明：语义/LLM 层当前**确实未实现**（PRD 里 L3/L4 原为预留），本管道选择如实标注跳过而非假装执行。若要真正启用，需平台配置 `LLMProviderConfig purpose=semantic` 并在适配层接入，属后续增量。
